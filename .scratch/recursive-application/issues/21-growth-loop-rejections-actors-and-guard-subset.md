# 21: Growth Loop: rejections, Actors, and Guard subset

**What to build:** Every way a Growth Iteration is refused or redirected, and the Specialist path. New tests that already pass reject the Iteration with the reason `no red`; a Plan with Python targets and no tests is rejected before Act; a Plan without Python targets skips the Test Writer and uses its red Target Cases as the red; a rejected Iteration is recorded as a lesson by the Librarian and undone with a hard reset and clean; a Plan naming an unknown or ineligible Actor is rejected before Act and counts as no progress; a Plan naming a registered Specialist invokes it in the Act slot; the Guard subset per Iteration is exactly the Target dataset, triage, answers, and the affected agents' datasets; wishes the system may not fulfil become policy findings.

Source: spec sections "Loop semantics", "Agent registry, roles, and Specialists", "Evals and traces" (Guard subset); ADRs 0007 and 0008; user stories 20, 21, 22, 25, 50, 56.

Deviations and judgement calls for the human to confirm:

- **`ineligible actor` is a reason distinct from `unknown actor`.** The seams document's Growth paragraph names one reason, `unknown actor`, for "an Actor that is neither implementer nor a Specialist"; ADR 0007 and the spec say "unknown or ineligible". A name no registry knows is `unknown actor: <name>`; a registered name that may not fill the slot is `ineligible actor: <name>`.
- **A Specialist is eligible only when its output type is the slot's contract.** `_actor_refusal` compares `entry.agent.output_type is REQUIRED_ROLES[default_actor].output_type`, so a `CodeReport` Specialist fills the Growth slot and not the Task slot, and a `WorkerOutput` Specialist the reverse; a required role other than the default (`planner`, or `implementer` in a Task Loop) is ineligible. ADR 0007 says only "the slot the Worker or the Implementer would otherwise fill".
- **A no-red rejection is a lesson like a Gate rejection.** The seams document says a not-red check "rejects the Iteration with reason `no red` and the output in the record"; the spec says every rejected Iteration is recorded as a lesson and reset. This took the spec: the Librarian is called, the tree reset, and the lesson committed, one Librarian call per no-red.
- **Every lesson in a run has the same commit subject, `ra: lesson from <run_id>`,** as the seams document names it; two rejected Iterations give two identical subjects (asserted).
- **The lesson summary and the log line are new literals:** `Rejected: <title>`, blank line, `plan.change`, blank line, `Run: <run_id>`, `Reason: <reason>`; the log line `Run <run_id>: rejected <title>: <reason>`. A Gate rejection's reason is `<first failed check>: <excerpt>` (`ty: ...`, `review: <notes>`, `evals: <regressed key>`).
- **The retry of a regressed Guard Case** runs one `runners.evals` over the datasets of the regressed keys with those keys as targets, and the cases that pass fill `guard_retry_passed`; the seams document says "over its dataset". Built in ticket 20, tested here.
- **The policy refusal is first,** before `no Target Cases`, `no tests`, the Actor check, and `_dataset_refusal`, so it lands before the append and before approval, as the seams document orders; `_refusal_before_act` took `state` for it and is shared, so a Task Plan naming a forbidden `target_paths` entry is refused the same way although the Worker never edits code.
- **The policy finding numbers itself:** `_RunState.policy_findings`, separate from `gaps_recorded`, so `policy:<run_id>:1` is the first policy finding of the run whatever gaps were recorded before it; the source prefix keeps the ids unique across sources. The seams document gives no id shape.
- **What counts as forbidden** is `is_protected(path, root)`, so every Protected Path (the Kernel, `docs/`, `tests/kernel`, `pyproject.toml`, a path outside the checkout) refuses a Plan, not only the four the ticket names, plus the string prefix `evals/frontier/`; only the first offending path is named in the reason and the finding. The check reads `target_paths` literally; a diff that touches such a path without naming it stays the Gate's `protected-paths` check to catch.
- **The Loop trusts the checks module's `red` flag** and never reads the exit code itself: the exit-code semantics of ADR 0008 live in `kernel/checks.py`; here 5 and 2 are tested only as not red.
- **Test scaffolding:** `_harness` gained `registry` (a Specialist added to the real registry) and `evals` (a scripted adapter answering each request in turn, for the retry); the glossarist borrows the Implementer's prompt file because the harness reads prompts from the real checkout; ticket 20's failing-`ty` test gained a scripted Librarian, since a rejected Gate now calls one.
