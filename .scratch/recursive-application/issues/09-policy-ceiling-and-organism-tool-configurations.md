# 09: Policy Ceiling and Organism tool configurations

**What to build:** The Organism owns which commands and paths each agent gets; the Kernel owns the Policy Ceiling no configuration may exceed and refuses to build an agent whose tools exceed it. Each role's tools do exactly what the spec grants: the Test Writer writes only under the Organism tests, the Implementer only under the Organism package and the README, the Librarian only under the Wiki, everyone else nothing; the shell allows the project's checks and read-only utilities and never git, install commands, network clients, or recursive deletes; no tool reads the env file or the git directory, and no tool writes anywhere a change would not reach the git diff.

Source: spec sections "Kernel, Organism, Protected Paths, and the write scope" and Testing Decisions seam 7; ADR 0001.

**2026-09-05, implemented.** Red to green through the seams document's five policy and nine tools tracer bullets: 28 tests in `tests/kernel/test_policy.py` over `src/recursive_application/kernel/policy.py`, and 33 tests in `tests/organism/test_tools.py` over `src/recursive_application/organism/tools.py`, driven by a new `tests/organism/conftest.py`. The Kernel module holds the ceiling as module constants (`FORBIDDEN_COMMANDS`, `FORBIDDEN_SUBCOMMANDS`, `DENIED_OPERATORS`, `UNREADABLE_PATTERNS`, `SECRET_ENV_PATTERNS`, `NETWORK_ALLOWED`), the `ToolConfig` contract, `validate_tool_config`, and `forbidden_reason`; the Organism module holds `SHELL_COMMANDS`, `ROLE_TOOL_CONFIGS`, `toolsets_for`, `ToolDescription`, and `describe_tools`. The write-scope rule is never restated: `validate_tool_config` asks `writable_globs()` and `WRITABLE_DIRS`, and the file tool's guard asks `is_writable`, both from `kernel/paths.py`.

The judgement calls behind the shape. `forbidden_reason` runs `shlex.split` first, because an unbalanced quote makes the harness shell skip its own allowlist check entirely (research §A3), so a command line that does not parse is itself a reason; then the denied operators as substrings on the raw line, because the harness runs the string through `/bin/sh`; then the first token; then a forbidden subcommand (the tokens after the first matching a forbidden sequence, so `uv add` and `python -m pip` are named in full); then the unreadable paths, as regexes over the raw line rather than over the tokens, so `open('.env')` inside a quoted Python snippet is caught: `(?<![\w.])\.env(?![\w.])` matches `.env` as a token, a path segment, or inside quotes while leaving `.env.example` readable, and `\.git(?:/|\b)` catches `.git` as a token or path prefix while leaving `.gitignore` readable. Path reads have to be caught here because the harness `Shell` has no path sandbox at all: `cat .env` leaks the key no matter what the file tool's patterns say (research §A3, probe).

`toolsets_for` builds the harness `FileSystem(root_dir=root, denied_patterns=UNREADABLE_PATTERNS, read_only=not write_globs)` and, when there is a write scope, wraps its toolset in a `WrapperToolset` subclass whose `call_tool` intercepts `write_file`, `edit_file`, and `create_directory`, canonicalises the path against `root` the way the harness does, and returns `refused: <path> is outside this agent's write scope` unless the path matches one of the agent's globs by `fnmatch` *and* satisfies `is_writable`. The scope is not expressed as the harness's `allowed_patterns`, because that list also filters the directory walkers: with it set, `list_directory('.')` returns `(empty directory)` (research §A1), which would blind an agent that is meant to read the whole checkout. The shell toolset is wrapped the same way, consulting `forbidden_reason` and replying `refused: <reason>`. Both refusals are ordinary tool replies, not exceptions and not `ModelRetry`, so nothing escapes the run and the model can correct itself. The git toolset is a `FunctionToolset` of five plain functions over `Repo(root)`'s read helpers, each returning a `GitError`'s message as its reply text.

The toolsets attach to an agent as `Agent(model, toolsets=toolsets_for(config, root))`. `capabilities=[FileSystem(...), Shell(...)]` is the harness's documented spelling, but it takes capability objects, not the wrapped toolsets this module returns, so `toolsets=` is the route the registry ticket needs; `FileSystem(...).get_toolset()` is a plain `AbstractToolset` and composes with `WrapperToolset` and `FunctionToolset` in one list without a name clash.

Deviations and judgement calls for the human to confirm:

- **Tools bullet 7's literal command contains `;`, which the ceiling itself forbids.** The seam names `python -c "import os; print(os.environ.get('OPENROUTER_API_KEY', 'unset'))"`, but `;` is in `DENIED_OPERATORS`, so `forbidden_reason` refuses it before the shell ever runs. The test uses the semicolon-free `python -c "print(__import__('os').environ.get('OPENROUTER_API_KEY', 'unset'))"` and asserts the same thing. A probe confirmed the test is sensitive: the same command through a `Shell` without `denied_env_patterns` prints `sk-or-test`.
- **`start_command` passes through `forbidden_reason` as well as `run_command`.** The seam names only `run_command`, but `start_command` takes the same `command` argument and starts the same process, so leaving it unguarded would be a hole in the ceiling.
- **`ToolConfig`'s list fields use `Field(default_factory=list)` rather than the seam's `= []`.** Identical behaviour; ruff's RUF012 fires on a bare mutable default when the pydantic base class (`Contract`) is imported from another module, as it is here.
- **An agent scoped to `<dir>/**` cannot create `<dir>` itself.** `fnmatch` requires the literal `/`, so `create_directory("src/recursive_application/organism/specialists")` is refused for a Specialist scoped to `src/recursive_application/organism/specialists/**`, while the Implementer (scoped to `organism/**`) can create it. The Specialist test therefore creates the directory as part of the layout. Worth deciding whether the scope should also admit the directories on the way to a glob.
- **`describe_tools` reads the tool names and descriptions synchronously** by following a `WrapperToolset` down to the `FunctionToolset` it delegates to (the harness `FileSystem` and `Shell` toolsets are `FunctionToolset` subclasses) and taking the first sentence out of the `<summary>` block pydantic AI builds from each docstring. `get_tools()` is async and needs a `RunContext`, which needs a live model, so it is not available to a deterministic Capability Inventory. The writing tools are left out of the list when the configuration has no write scope, keyed off `WRITING_TOOL_NAMES`, the same constant the guard uses; the harness's `read_only=True` removes exactly those three.
- **"First sentence" ends at a full stop followed by whitespace or end of string and not preceded by a single letter**, so `start_command`'s description keeps its `(e.g. a server or watcher).` instead of being cut at `(e.`.
- **`denied_patterns` is `UNREADABLE_PATTERNS` verbatim (`.env`, `.git/**`)** rather than the `.git/*` the working notes suggested; the research document's probe shows both spellings deny `.git/config` and `.git/objects/deep.txt`, and reusing the Kernel constant keeps one source of truth.
