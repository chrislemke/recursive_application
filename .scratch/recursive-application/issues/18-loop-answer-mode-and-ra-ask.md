# 18: Loop, Answer Mode, and `ra ask`

**What to build:** `ra ask "a question"` runs one complete Loop in Answer Mode: Sense collects findings, Triage performs its Reflection and picks Answer, the Kernel builds one Target Case from the request and the generic answer rubric, the Worker answers, the Gate runs the judge, a failed judge feeds its reason into the next Iteration, and after the iteration limit the best output is printed with a warning and a Sensor Finding is recorded. The Run Record and the trace file exist afterwards. A clarification gap prints the questions and stops. At a terminal the Operator is asked for feedback. This is the thinnest complete path through all five phases and the first real CLI command; the runner's interface is written here in full so the following three tickets only add cases.

Source: spec sections "Loop semantics" (Answer, stop rules, clarification) and "CLI"; Testing Decisions seams 1 and 9; user stories 1, 2, 5, 11 to 15.

**Blocked by:** 14 (Agent runtime), 15 (Eval task functions, custom evaluators, and `ra evals`), 16 (Sensors), 17 (Gate)

**2026-09-05, implemented.** Red to green through cases 1 to 5 of the Loop seam: 13 tests in `tests/kernel/test_loop.py` over `src/recursive_application/kernel/loop.py`, plus one appended test in `tests/kernel/test_records.py` for the records amendment `Plan.dataset`. The runner is synchronous and owns no side effect: agents go through the injected `AgentRunner`, and the checks, the red check, the evals, the approval, the clock, and the Trace Store through the injected `Runners`, so a test replaces the world with six lambdas and a scripted model. `tests/kernel/loop_support.py` holds the two things the tests share: `scripted_models`, a `model_factory` whose `FunctionModel` reads the `Role:` line of the State Bundle out of the request's instructions, pops that role's next scripted output (a contract as the `final_result` tool call, a string as text, an exception raised where the model would have answered), reports an optional `RequestUsage`, and records every request so a test can read the Loop position and the prompt an agent received; and the `checkout` fixture, which lays the `git_repo` out like the real checkout (the tracked `evals/`, `wiki/`, `README.md`, an Organism stub, one commit, `.ra/` created and already ignored).

One run reads: `RunRecord` stamped by the injected clock, `runners.tracing(run_id)` for the Trace Store file, `sensors.collect` for Sense, Triage for Decide when the Mode is `None`, then Answer Mode. Answer writes the one Target Case (`answer-<run_id>`, the request as `inputs`, `ANSWER_RUBRIC` as an `LLMJudge` rubric with `include_input: true`) to `.ra/tasks/<run_id>/cases.yaml`; each Iteration runs the Worker, writes `output.md`, calls `runners.evals(EvalRequest(...))` with that file as the `task_dataset`, compares against the latest persisted report, gathers `trace_findings` over this run's spans, and hands `GateInputs(mode=Mode.ANSWER, ...)` to the Gate. The Iteration is appended to the Run Record as it ends, with its usage, so a crash leaves the record behind. A failing judge feeds its reason into the next Worker prompt under `Previous attempt failed because:`.

Judgement calls behind the shape: Triage sits inside Iteration 1 because an Iteration is one pass through the five phases and Decide is one of them, which also keeps its cost inside `RunRecord.total_usage`, the sum the budget rule reads; the stop rules are checked before each Iteration in the seams document's order (iteration limit, wall time, budget, no progress) and an open breaker is not a pre-check but a refusal raised by the agent runtime at the call, so its reason names the role that was refused; and a rule that stops an Answer run which already produced output (the iteration limit, no progress) returns that output as best effort with outcome `rejected` and exit 1, while wall time, budget, an open breaker, and a clarification gap abort with exit 2, as the seam says.

Deviations and judgement calls for the human to confirm:

- **Triage runs inside Iteration 1 and its usage lands in that Iteration's record.** A clarification gap and an open breaker therefore leave one `IterationRecord` with outcome `aborted` behind rather than none. The seams document says "nothing else runs" for the clarification, not that nothing is recorded; without the record, Triage's cost would fall outside `total_usage`.
- **The budget rule is the plain sum, `estimated_cost(record.total_usage) >= budget`, checked before each Iteration**, because the spec says the budget is "summed over the run". The seams document's budget case says "each scripted Worker call reports `cost_usd=3`" against a 5 USD budget; with the plain rule 3 is not yet 5, so the test scripts the price on every model response, and Iteration 1 spends 6 USD (Triage plus the Worker) before the second one is refused. The alternative reading is a predictive rule ("the next Iteration would exceed the budget", estimated from the last one), which would fire on the Worker's 3 USD alone.
- **The remaining budget is not passed to each agent call as a cost limit.** The seams document's stop-rule sentence asks for it, but `AgentRunner.run(entry, prompt, *, bundle)` takes no cost limit and `kernel/runtime.py` is not this ticket's file; it sets `cost_limit=settings.ra_budget_usd` per call. The before-Iteration check is the only budget guard today.
- **A Mode the runner does not run yet (`task`, `growth`) ends the run as an internal error** (`NotImplementedError`, outcome `error`, exit 3) instead of silently running the Answer flow, with a test of its own. This is not one of cases 1 to 5; it exists because Triage may well answer `growth` to the manual criterion's question, and answering it as if it were an Answer would be a silent fault. Deviations and judgement calls for the human to confirm:

- **The terminal check is a module function, `stdin_is_a_terminal()`, and not an inline `sys.stdin.isatty()`.** Typer's `CliRunner` replaces `sys.stdin` inside `invoke`, so a test cannot patch the object the command will see; making the check a module attribute keeps it replaceable the way the clock and `build_context` are. It is still `sys.stdin.isatty()` in production.
- **A second prompt, `What was wrong?`, is printed before the comment line is read.** The seams document names only `Was this answer useful? [y/n]` and then takes "the next input line" as the comment; a terminal that reads a line without asking for one is not usable.
- **Only an answer starting with `n` counts as negative.** An empty line or anything else leaves no entry, because an Operator who presses Enter has not judged the Answer.
- **The one error handler re-raises `typer.Exit` and `typer.Abort` before its catch-all.** Both are `RuntimeError` subclasses in Click, so the catch-all would otherwise turn a clean exit into `internal error`.
- **Every command's body is a nested `action() -> int` handed to `_run_command`.** It is the only way to have one exit-code rule in one place: the function returns the code, and the handler is the only thing that raises `typer.Exit`.
- **`build_context()` calls `require_api_key()` for every command**, as the seams document says, so `ra status` and `ra wiki lint` need a key even though neither reaches a model. Confirmed by the smoke run: with no `OPENROUTER_API_KEY` in `.env`, `uv run ra status` printed `OPENROUTER_API_KEY is not set; put it in .env or the environment` and exited 2.
- **`improve` is still the stub.** Ticket 22 owns bullet 4 of the CLI seam.
- **Four tests were green on their first run**: the three exit-code rows (1, 2, 3) and the clarification-questions row of bullet 2, because bullet 1's implementation already returned `result.exit_code` and printed the questions; and the "no feedback when stdin is not a terminal" row of bullet 3, because no feedback code existed yet.
