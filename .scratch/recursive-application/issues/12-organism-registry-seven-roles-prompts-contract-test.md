# 12: Organism registry: seven roles, prompts, registry contract test, documentation pointers

**What to build:** The Organism exposes one registry the Kernel can load and trust. Each entry carries a name, a Pydantic AI Agent with no model set, a model tier, the phases it may act in, its tool configuration, its guides, its prompt path, and the dataset that proves it. The seven required roles are present with the right output types; each has a prompt file holding only its own job; the coding roles list the Coding Guide as a guide. The Kernel's registry contract test is the test that protects the Kernel from a bad Improvement, and the documentation pointer test keeps the Coding Guide and the Constitution honest.

Source: spec sections "Agent registry, roles, and Specialists" and "The Coding Guide and the guides mechanism"; Testing Decisions seams 6 and 10; ADR 0007.

**Blocked by:** 03 (Data contracts and the Run Record), 07 (Constitution), 08 (Wiki module and seed Wiki), 09 (Policy Ceiling and Organism tool configurations), 11 (Seed eval datasets for the seven roles)

**2026-09-05, implemented.** Red to green through the seams document's seven tracer bullets: 33 tests, 29 in `tests/kernel/test_registry.py` and 4 in `tests/kernel/test_doc_pointers.py`, over `src/recursive_application/kernel/registry.py`, `src/recursive_application/kernel/pointers.py`, `src/recursive_application/organism/agents.py`, and the seven prompt files under `src/recursive_application/organism/prompts/`. `RegistryEntry`, `RoleSpec`, and `Registry` are frozen dataclasses rather than `Contract`s, as the seams document's design note says, because an `Agent` is not Pydantic-serialisable; `REQUIRED_ROLES` is a plain mapping literal. The output-type check reads `entry.agent.output_type`, probed rather than guessed (`pydantic_ai 2.40`: a public attribute, `str` when no `output_type` was given, `agent.model is None` when no model was); in typing terms it is an output specification union rather than a class, so the message helper takes `object` and falls back to `str()`, which is what `ty` demanded. `validate_registry` runs eight passes over all the entries in the Interface's order (duplicate name, missing required role, `RoleSpec` mismatch, Specialist outside Act, agent with a model, missing or empty file, prompt that does not name its phase, tool configuration above the ceiling), each raising `RegistryError` naming the entry and the fault; passes rather than one loop per entry, so the order the document lists is the order a registry with two faults reports. `load_registry` imports `organism.agents` inside the function, so the Kernel package still imports with no Organism present. The Organism side builds each entry through one private helper, so adding a Specialist stays one line plus a prompt, a tool configuration, and a dataset (ADR 0007). `kernel/pointers.py` matches single-backtick spans that hold no newline, which is what keeps the Coding Guide's fenced block of the four check commands from being read as one giant pointer.

The prompts were written as real prompts on the first pass, because bullet 2 runs them and the ticket 15 evals judge them. Each is one line naming the phase and the artifact, then that role's own job, 21 to 33 lines. The reasoning behind them: the Constitution and the Coding Guide are prepended by the Kernel, so a prompt that repeats them spends the model's attention twice and drifts when they change; every prompt therefore holds only what the Kernel cannot say for the role, which in practice is the meaning of its own output fields. Triage gets the five gap kinds each defined by what would close it, the rule that any gap but clarification makes the Mode `growth`, and the rule that `available` may name only what the Capability Inventory lists. The Planner gets the loop-element table by reference and then in its own terms (the dataset that senses and gates the change, the tool configuration, the Actor, the Target Cases, the lesson), `tests` as one-sentence behaviours at a public interface with literal expected values for every Python target, `target_paths`, `target_cases` as append-only, `actor` including when a Specialist fits, and `needs_human` for anything only the human may grant. The Test Writer is told to go red and stop, what counts as red and what does not, and to put the pytest run in `checks`; the Implementer to go green under its write scope, never to edit a test, to run the four checks of the Coding Guide and list them in `checks` by their contract names, and that a false green costs the run while an honest red costs one Iteration. The Worker is told to report every gap it meets in `gaps`, to cite the Capability Inventory as the only source for what is available, and to answer questions about itself from the Constitution and the Inventory in front of it, ratios as they stand. The Reviewer applies the Coding Guide's three test rules, looks for eval gaming and Plan mismatch, and on `verdict: reject` names the first violated rule in the first sentence of `notes`. The Librarian writes through its Wiki tool only, records a capability page with the `- Commit: ` and `- Dataset: ` lines, a lesson for a rejected Iteration, a `next-frontier-<capability>.md` proposal when a ladder turns green, appends one log line per run, and returns a one-paragraph summary naming each page by path.
