# 19: Task Loop with escalation and gap recording

**What to build:** A Task that needs iteration runs the Task Loop: the Planner writes a Plan with Target Cases and optionally an Actor, the Kernel writes the cases as runtime data for that run and never into a tracked dataset, shows Plan and cases as YAML for approval unless skipped, the Actor (Worker by default) writes its output under the run's task directory, the Gate evaluates, and the Loop iterates until pass or a stop rule. A Capability Gap in the Plan or reported by the Actor escalates to a Growth Loop with a fresh approval; gaps not escalated are recorded as reflection findings.

Source: spec section "Loop semantics" (Task Loop); user stories 3, 4, 19, 23, 24; glossary entries Task Loop, Definition of Done, Actor.

**2026-09-06, implemented.** The Task Loop beside the Answer Loop in `src/recursive_application/kernel/loop.py`, driven by eleven new tests in `tests/kernel/test_loop.py` (28 in the file, all green). `run` now dispatches by Mode: `_answer` as before, `_task` for the Task Loop, `_unsupported` for anything else. One Task Iteration is `_plan_act_and_gate`: the Planner runs at `phase="decide"` on the Task and the open findings, its Plan is carried by a frozen `_TaskPlan` (Plan, cases path, dataset name, target keys) and recorded on `IterationRecord.plan`; the Plan's Target Cases are written to `<ra_dir>/tasks/<run_id>/cases.yaml` in the pydantic-evals format (`must_contain` entries as `Contains`, `expected_output` as `EqualsExpected` with the expected output on the case, `rubric` as `LLMJudge` with `include_input: true`, in that order); the human sees `yaml.safe_dump({"plan": ..., "target_cases": [...]})` through `runners.approve` unless `options.yes`, and a refusal is the stop reason `approval refused` (aborted, exit 2); the Actor is `plan.actor or "worker"`, called at `phase="act"` with the Task and the Plan as YAML; its `WorkerOutput.content` goes to `output.md` and the Iteration's `output_path` points there; the evals runner is asked for `dataset="task-<run_id>"` with targets `task-<run_id>/<case name>`; the Gate is `GateInputs(mode=Mode.TASK, eval_delta=..., anomalies=..., review=...)`.

The judgement calls behind that shape. The Reviewer is the only Gate input that costs a model call, and the spec says the Kernel gathers Gate evidence in check order and stops at the first failure to save cost, so the Iteration evaluates the Gate once without a Review and calls the Reviewer only when the sole failing check is `review`; the Gate marks `review` `skipped` after an earlier failure either way, so the recorded result is the same and a failed Iteration costs nothing extra. The unknown-Actor rejection needed a place for its reason, and the seams document keeps `IterationRecord` unchanged, so the reason goes where it can still do work: into the next Iteration's Planner prompt under the existing `RETRY_HEADING`, the same convention a retrying Worker already gets. Gaps are handled where they are recognised, in `_handle_gaps`, called on the Plan and again on the Actor's output: a gap carrying `needs_human` (or a `clarification` gap) is written to the `FindingStore` as `reflection:<run_id>:<n>` before anything escalates, so a Plan that mixes both kinds loses neither; any other gap sets `record.mode` to Growth, asks for a fresh approval with the gaps rendered as YAML, and then hits the unsupported-Mode error that ticket 20 replaces. Best effort became Answer-only: a Task Loop's output is measured against Target Cases the human approved, so an output that never passed them is not a result, and the iteration limit ends a Task run as `aborted` with reason `iteration limit` (the seams document's case 6b).

Deviations and judgement calls for the human to confirm:

- **Interface additions to record as amendments:** `TASK_DATASET_PREFIX = "task-"`, `TASK_ACTOR = "worker"`, `APPROVAL_REFUSED = "approval refused"`, `UNKNOWN_ACTOR = "unknown actor"` in `kernel/loop.py`.
- **The rejection reason reaches the next Planner, not the Iteration record.** The seams document says the reason `unknown actor: <name>` is "recorded on the Iteration" with `gate=None`, but `IterationRecord` has no reason field and the document says the contract gains nothing, so the Iteration holds the Plan, `outcome="rejected"` and `gate=None`, and the reason goes into the next Planner prompt under `Previous attempt failed because:`. Tickets 20 and 21 need the same for `no red`, `no tests`, and `policy`; if the reason should be persisted, `IterationRecord` needs a field.
- **A Plan gap asks for approval once, not twice.** The seams document escalates before the Plan is shown ("A Plan with `gaps` escalates ... Otherwise the Kernel writes `plan.target_cases`"), so a Plan-gap escalation shows the human one text, the gaps; only a gap the Actor reports produces the two approvals the ticket's brief names, because the Plan was already approved.
- **`--yes` skips the escalation approval too.** The seams document calls it "a fresh approval" without saying whether the flag covers it; treating it like every other approval keeps `ra ... --yes` unattended.
- **Escalation happens before the Actor's output is written.** A `WorkerOutput` carrying a gap escalates before `output.md` is written and before the Iteration is recorded, so an escalating Iteration leaves the record's `output` empty; ticket 20 may want the draft kept as evidence.

- **The Actor's retry note is the first Target Case's judge reason** (`_judge_reason`, shared with the Answer Loop), not a summary of every failed Target Case.
- **A gap's `reflection` finding renders its details as three lines** (`kind:`, `how_to_acquire:`, `needs_human:` with the entries comma-joined); the seams document names the three fields but not the rendering.
