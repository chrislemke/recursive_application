# 16: Sensors

**What to build:** One call collects every open Sensor Finding: red eval cases from the latest report (one finding per red non-frontier case and one per frontier capability naming its lowest red rung), trace anomalies over the Trace Store by the five deterministic rules, unaddressed negative feedback from the feedback file, open questions from the Wiki including frontier proposals, and the reflection and policy findings the Kernel wrote during runs. Findings come back ranked by severity, then age.

## Comments

**2026-09-05, implemented.** Red to green through the seams document's seven tracer bullets: 14 tests in `tests/kernel/test_sensors.py` against `src/recursive_application/kernel/sensors.py`, importing only the names the Interface lists plus the contracts of `records.py`, `evals.py`, `paths.py`, and `organism/wiki.py`. Five Sensor functions are pure over their inputs, so every rule is exercised with a literal report, span record, feedback entry, or open question; `collect` is the only call that opens the runtime directory and the Wiki, and its two tests run under `tmp_path`.

The judgement calls behind the rules. `eval_findings` skips any case whose dataset starts with `frontier/`, so a red rung reaches the list once as its capability's finding rather than once per case, which is what keeps each Growth Iteration to one rung. `trace_findings` walks the runs of `spans_by_run` in order and lets each of the three span rules fire at most once, then adds the slow-run finding for the latest finished run and one costly-run finding per run, in the order the Interface lists the rules. The repeated-tool-call rule counts spans by `(gen_ai.tool.name, gen_ai.tool.call.arguments)`, the two attributes pydantic-ai's instrumentation writes on an `execute_tool <name>` span; the validation-retries rule reads the `validation_retries` attribute the agent runtime of ticket 14 will write on its own `kernel.agent_run` span, because an output-validation retry emits no span of its own. The slow-run median is taken over the last twenty finished runs sorted by `started_at`, the latest included, and a run that has not finished is left out of the median rather than counted as zero. `collect` pairs each finding with the age of the evidence behind it as it gathers (the report's `created_at`, the run's `started_at`, the feedback's `at`, the stored `at`, the Wiki page's `st_mtime` as a UTC datetime), drops every id that any Run Record names in `findings_addressed`, and sorts by `(severity rank, age)` with a stable sort, so equally severe and equally old findings keep the order the Sensors produced them in.

Deviations and judgement calls for the human to confirm:

- **`stored_findings` returns findings exactly as they were written, with no severity re-derived from the source.** The seams document's severity table gives `medium` to a `reflection` finding and `low` to a `policy` one; the Sensor does not enforce that, so the writer sets it, which will be the Loop runner of tickets 18 to 22. Bullet 7's test writes its `policy` finding at `low` accordingly, so the ranking is proven but the table is not enforced anywhere yet.
- **Public names beyond the Interface**, none of which any test imports: `FRONTIER_PREFIX`, `TRACES_SUBDIR`, `RUNS_SUBDIR`, `REPORTS_SUBDIR`, `SEVERITY_RANK`, `UNDATED`, `TOOL_NAME_ATTRIBUTE`, `TOOL_ARGUMENTS_ATTRIBUTE`, `VALIDATION_RETRIES_ATTRIBUTE`. Three are worth recording as seams other tickets will reach for: `SEVERITY_RANK` is the order the State Bundle of ticket 13 needs to take the ten most severe findings, and `VALIDATION_RETRIES_ATTRIBUTE` is the exact attribute name the agent runtime of ticket 14 has to write.
- **The runtime subdirectory names are unpacked from `RA_SUBDIRS`** (`TRACES_SUBDIR, RUNS_SUBDIR, _TASKS_SUBDIR, REPORTS_SUBDIR = RA_SUBDIRS`) rather than spelled again here, so the path rule stays the single source. A fifth entry in that tuple breaks this import loudly, which is the intent, but it is a coupling to the tuple's order.
- **`UNDATED` is `datetime.min` in UTC**, the age a finding gets when its evidence carries none: no saved report at all, or a trace anomaly whose Run Record is gone. Such a finding sorts oldest inside its severity band. The seams document does not say which way it should go.
- **A missing `gen_ai.tool.call.arguments` counts as the empty string** when the repeated-tool-call rule groups spans, so three calls to one tool made with content capture off still count as a repeat. The seams document names both attributes but not the missing one.
- **The validation-retries rule takes the highest `validation_retries` value on any span of the run**, not the sum across spans, so two spans reporting one retry each are not an anomaly.
- **The error-span finding names every ERROR span of the run in its `details`** while staying one finding per run.
- **Naive timestamps are read as UTC before ranking**, so a hand-edited feedback or findings line without a zone cannot crash `collect` on a comparison between aware and naive datetimes.
- **One test was green on its first run**: `test_collect_puts_the_older_of_two_findings_of_the_same_severity_first`. Bullet 7 says the list is ranked by severity then age, but its own fixture gives every finding the same timestamp, so the age half of the ranking had no test. The extra test is the ticket's "ordered by severity then age" criterion; the sort was already written for bullet 7, so it could not go red honestly. It was checked by mutation instead: removing the age from `collect`'s sort key makes that test, and only that test, fail.
- **One correction inside the loop, recorded rather than hidden.** The first `eval_findings` implementation already handled `report is None`, which its own test did not ask for. Before writing the `None` test the handling was taken out again, the first test confirmed still green, the `None` test watched failing with `AttributeError: 'NoneType' object has no attribute 'cases'`, and the handling put back. Every other test in the file went red before its code existed, for a missing name or a failed assertion.
