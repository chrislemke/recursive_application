# 15: Eval task functions, custom evaluators, and `ra evals`

**What to build:** `ra evals` runs one dataset or all of them, prints the report, persists it with the latest pointer, and prints where it went. A task function exists for every dataset kind and a Kernel test proves every dataset file maps to one. Two custom evaluators check for secrets in output and for Organism-only target paths. The Judge Model is set through the pydantic-evals default judge before any run, so datasets never name a model. The test-writer and implementer datasets are marked expensive and run only in the full suite.

Source: spec sections "Evals and traces" and "CLI"; Testing Decisions seam 4; ADR 0005.

**Blocked by:** 11 (Seed eval datasets for the seven roles), 14 (Agent runtime)

**Status:** done

- [ ] The seam is written in the seams-document format and confirmed by the user before the first red test
- [x] A task function per dataset kind (triage, planner, test-writer, implementer, answers, reviewer, librarian, frontier) runs the right agent through the agent runtime; a test asserts every file under the evals directory has a task function
- [x] The no-secrets evaluator fails an output containing a key-shaped token; the Organism-only evaluator fails a Plan whose targets include a Protected Path
- [x] The default judge is set to the Judge Model before any dataset runs; a dataset naming a model is rejected
- [x] `ra evals [--dataset NAME] [--repeat K]` accepts a role name or a frontier capability, prints the report and the persisted path, and exits 0; an unknown dataset exits 2
- [x] The test-writer and implementer datasets are excluded unless the full suite is requested
- [x] Tests fake every model; nothing reaches the network
- [x] All four checks exit 0
- [ ] Manual, for the human afterwards: `uv run ra evals --dataset triage` against OpenRouter persists a report

Every task runs the same three steps: read the case's inputs, assemble the production State Bundle for a `LoopPosition` its kind names, run the role through `AgentRunner`, and render the result. `ROLE_POSITIONS` is the one table mapping a dataset kind to its role, Loop Mode, and phase, so the Reviewer is evaluated at the Gate of a Growth Loop and the Worker in the Act phase of an Answer Loop; Triage is placed in Answer Mode because the Mode is what it decides. The two evaluators are tested at their real seam, a temporary dataset spelling `- NoSecrets` and `- OrganismTargetsOnly` and evaluated through `load_dataset` and `results_from`, which also proves they are registered. `run_evals` refuses an unknown name and every dataset that names a model before it touches the judge, sets the judge once, then runs each dataset through `evaluate_sync(task, progress=False, repeat=repeat)` and saves one report through `ReportStore`. Nothing reaches the network: every role runs on a `TestModel` or `FunctionModel` handed to the runner through `model_factory`, and the judge is a `TestModel` too.

Deviations and judgement calls for the human to confirm:

- **Seam amendment: `EvalContext` gains `ra_dir: Path`, `wiki: WikiReader`, and `budget_usd: Decimal`.** `assemble_state_bundle` needs all three, and an eval that assembled anything less than the production bundle would not be evaluating what the Loop runs.
- **Seam amendment: `task_for` takes and returns `str`.** `load_dataset` pins `Dataset[str, str, dict[str, Any]]` and `EvalCase.inputs` is `str`, so the mapping-shaped datasets hold their mapping as a YAML block scalar and the task `yaml.safe_load`s it first (`planner`, `test-writer`, `implementer`, `reviewer`, `librarian`); a case whose inputs are not a mapping raises `DatasetError`.
- **Seam amendment: a role that needs a scratch checkout runs inside `with entry.agent.override(toolsets=toolsets_for(entry.tools, scratch)):`.** Only where the toolsets are rooted changes, so the Librarian still writes `wiki/pages/...` and the Implementer still writes `src/recursive_application/organism/...`, exactly as in production. The Librarian test asserts the real checkout's `wiki/pages/capabilities/repo-history.md` does not exist afterwards, which is what proves the rooting.
- **Seam amendment: `run_evals` takes `judge_model: str | Model` and `judge_setter: Callable[[Any], None]`.** Making the judge itself replaceable is what keeps it off the network in the tests, which pass a `TestModel(call_tools=[])`. `Any` is the setter's parameter type because pydantic-evals declares `set_default_judge_model(model: Model | KnownModelName)` and `KnownModelName` is a literal union of the names it ships with, which no configured model name satisfies; `Callable[[str | Model], None]` therefore fails `ty`.
- **A probe settled what the un-replaced judge does.** With the default judge left in place, an `LLMJudge` case does not crash the run: pydantic-evals records an evaluator failure (`UserError` for the missing provider key) and the report is still saved. Replacing the judge was still preferred, because with the `TestModel` judge the same case produces a real assertion instead of a failure, which is what a test of `run_evals` should see.
- **The judge default is restored with `monkeypatch.setattr(llm_as_a_judge, "_default_model", ...)`.** pydantic-evals offers a setter and no getter for a process-global, so the test records the module attribute to put it back rather than leaking a `TestModel` judge into the rest of the session.
- **The Librarian task reads its scratch Wiki with pathlib and three constants of its own** (`WIKI_DIRNAME`, `WIKI_PAGES_DIRNAME`, `WIKI_LOG_FILENAME`) instead of importing the Organism's `Wiki`, so the Kernel keeps importing nothing from `organism/wiki.py` (the reason `kernel/wiki_protocol.py` exists). The `pages` mapping is keyed by Wiki-relative POSIX path and `log_tail` is the log's last non-empty line, which on the seed Wiki is its heading.
- **A scratch checkout is `pyproject.toml`, `src/`, `tests/`, and `evals/`, and its project file gains `pythonpath = ["src"]`.** The checkout is installed into the virtualenv as a path entry, so without that line the scratch copy's pytest would import the real package and the role's edits would be invisible. The line is inserted into the existing `[tool.pytest.ini_options]` table, which is the only edit made to the copied file.
- **The Test Writer's `changed_files` are read from the filesystem, not from its own `CodeReport`.** The task takes a SHA-256 snapshot of the scratch checkout before and after the run and reports every file that differs, sorted, repo-relative POSIX, so a role that writes outside `tests/organism/` cannot hide it from the dataset's judge. When it changed nothing, the render is `pytest_exit: 5` and `red: false` (`classify_red(5, ...)`) rather than a pytest run over the whole suite.
- **The Implementer's `pytest_exit` and `green` come from `run_red_check` on the case's test files, while `checks_clean` is all four checks passing** through `run_checks` on the same scratch checkout; `ruff_format`, `ruff_check`, and `ty` are those checks' booleans. The seams document names the six fields but not which run produces which; this keeps `green` about the Plan's tests and `checks_clean` about the Gate's meaning of clean.
- **The expensive exclusion applies to `names=None` only.** An explicit `--dataset test-writer` runs it, which is what the ticket's "run only in the full suite" means for a human who asks for that dataset by name.
- **The expensive selection is tested with empty stand-in datasets under a temporary evals directory**, one per kind, rather than by running `test-writer.yaml` and `implementer.yaml`: `run_evals` builds a task for every selected dataset, so the stand-ins prove the selection rule and the existence of all eight task functions without copying the checkout or starting a subprocess. The task functions for `test-writer` and `implementer` are therefore written but never driven by a model in the suite, as the ticket asks.
- **`NoSecrets` names the pattern that matched, never the token**, so a failing eval report never carries the secret it caught. `OrganismTargetsOnly` reads the output as YAML and passes when it is not a mapping or names no `target_paths`, because the Worker's prose and the Librarian's render name no targets.
- **`assert_no_model` also refuses a dataset-level `evaluators` entry** that names a model, not only a case's, and reads the raw YAML so a file the loader would reject is still refused for this first.
- **A bullet added beyond the list: the Librarian task.** It is a cheap dataset that `ra evals` runs by default, and without a test its scratch-Wiki setup and its rendering would be the only production path in this module that nothing exercises. The test drives a `FunctionModel` that calls `write_file` once and then answers, and it was green on its first run; a mutation (keying `pages` by file name instead of Wiki-relative path) was used to confirm it bites.
- **Two tests were green on their first run**: the `run_evals(["nope"])` refusal, because the selection built for the expensive-datasets test already carried it, and the Librarian task test above.

Deviations and judgement calls for the human to confirm:

- **`evaluate_request` names its dataset from `request.dataset`, then the prefix of `request.targets[0]`, then the file stem.** The Loop sets `dataset` to `answer-<run_id>` and its target key to `answer-<run_id>/answer-<run_id>`, so the two agree by construction and `compare` finds the Target Case; the two fallbacks keep a request that predates the field working.
- **`kernel/eval_tasks.py` imports `EvalRequest` from `kernel/loop.py`.** The contract lives with the Loop that sends it and `loop.py` imports nothing from this module, so there is no cycle; the alternative, a third module for one contract, was not worth it.
- **The judge is set for a task dataset too**, even though the Loop's Answer case is an `LLMJudge` and nothing else in that file needs one, because the setter is process-global and the run must not inherit whatever the last caller left behind.
- **`--all` is the parameter `everything`**, since `all` is a builtin; the flag the Operator types is still `--all`.
- **`ra evals` generates its run id as `RunRecord(mode=Mode.TASK).run_id`**, the same generator the Run Records use, so a report saved by hand is named like every other one. It is the run id the report carries, not a Run Record on disk.
- **The scratch directory for eval checkouts is `.ra/scratch`** (`SCRATCH_DIRNAME` in `kernel/cli.py`). The seams document names `EvalContext.scratch` but not where the CLI points it.
- **No test was green on its first run for this ticket's bullet**; all three `evals` tests failed on the missing `cli.run_evals` attribute, and the `evaluate_request` tests on the missing function and then on the dataset name.
